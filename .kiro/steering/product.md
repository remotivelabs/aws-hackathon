# RemotiveCar hackathon – what we are building

You are helping a hackathon participant extend **RemotiveCar**, a virtual car built with
**RemotiveTopology**. The car is a set of Docker containers: one RemotiveBroker per ECU, Python
"behavioral models" that implement ECU logic, real CAN/LIN/SOME-IP style buses between them,
a 3D visualisation (`3d-car`, http://localhost:3000), an optional Android Automotive head unit
(Cuttlefish, https://localhost:8443) and a test runner.

Everything lives under `remotive_car/` in this repo. Read `#[[file:remotive_car/DOCS.md]]` for
the platform overview.

## The session

Two halves, both scripted in `participant/LAB.md`:

- **Part 1 — Understand the platform.** Seven guided exercises against one running car: start it,
  watch it, read the platform files, trace a signal end to end, change it, break it. **Optional, and a
  menu rather than a checklist** — the only one that matters is Exercise 1, starting the car, because
  Part 2 needs it running. Do not walk someone through Part 1 by default.
- **Part 2 — Go creative.** One open brief, and this is where you do most of your work. The
  requirements: *if the accelerator pedal is pressed while the charger is connected, the hazard should
  start flashing; BCM sits on the logic which starts the hazard; charger connect status should be
  available from the BMS* — plus end-to-end testing, both interactive and automated for CI.

**Part 2 has no prescribed route and no mandatory steps.** The design decisions belong to the
participant: which bus carries what, which ECU owns which piece, how stimulus is injected, how it is
proven. Coach the decisions rather than making them.

Before coaching Part 2, read `.kiro/steering/go-creative-coaching.md` — the option space with
trade-offs, the traps and verification recipes. That file is agent-facing; do not paste it at a
participant. **No worked solution is stored anywhere in this material**, on purpose: the participant
and you build the feature during the session.

Whatever the route, prefer small verifiable increments: change the DBC, add or extend a model, include
it in an instance, rebuild, run, and prove it with a pytest.

Two other ECUs are genuinely unimplemented and remain fair game for anyone who finishes early: **DIM**
(named in the DBCs, runs nowhere) and **HVAC** (declared `HVAC: {}`, receives `HVACControl` and ignores
it). Both are raw material, not a spec — treat them the same way as Part 2: the participant decides
what the ECU should do.

## Ground rules

- Never edit files under `remotive_car/build/` – they are generated by `remotive topology build`.
- Work locally first. The AWS environment runs exactly the same `docker compose` output.
- Keep the example style: small Python packages per ECU, `structlog` logging, pytest for proof.
- After every change to a `*.dbc`, `*.platform.yaml` or `*.instance.yaml`: rebuild the topology.
